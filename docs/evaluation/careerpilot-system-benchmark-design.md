# CareerPilot RAG 与记忆系统评测集建构说明

## 1. 建构目标

这套评测不是从 `rag/`、`memory/` 等代码目录反推若干测试题，而是沿着下面的链路构造：

> 产品目标 → 用户旅程 → 真实任务场景 → Agent 决策点 → 系统能力 → 可执行 Case

CareerPilot 的产品目标是帮助学生和职业早期用户理解自己、探索方向、验证假设并推进下一步。因此完整评测分为三层：

1. 单元与集成测试：验证函数、状态机、数据隔离和工具接口是否符合契约。
2. RAG 与记忆子系统基准：在冻结数据上验证召回、隔离、隐私边界和生命周期。
3. AgentEval：在情绪澄清、方向探索、外部调研、行动执行、长期复盘五类用户场景中验证端到端决策。

本轮输出聚焦第二层，同时与现有 AgentEval 数据集互补。RAG 和记忆是 Agent 完成用户任务的机制，不被当成用户业务场景。

## 2. 从用户任务到系统 Case

### 2.1 提取业务决策点

对每类用户任务，先判断 Agent 在运行时需要做什么决定。例如用户问“AI 产品经理需要哪些能力”，关键决策包括：

- 是否需要外部资料，而不是仅凭模型常识回答；
- 应检索哪个领域、是否拆分查询、是否需要多来源证据；
- 资料是否足够新，是否存在相互冲突的旧信息；
- 是否错误读取了其他用户的私有材料。

用户跨会话继续规划时，关键决策包括：

- 哪些历史信息与当前问题相关；
- 短暂情绪是否不应进入长期记忆；
- 敏感记忆是否只有在用户明确要求时才能进入上下文；
- 用户更正后，旧记忆是否退出有效状态；
- 重复表达是否被去重。

### 2.2 控制变量设计

每个 Case 只突出一项主要变化，形成可诊断的对照：

- 有相关资料 / 无相关资料；
- 正确领域 / 相同关键词的错误领域；
- 当前资料 / 过期资料；
- 当前用户资料 / 其他用户资料；
- 普通记忆 / 敏感记忆；
- 普通对话 / 明确要求记住；
- 原偏好 / 明确更正后的新偏好。

这种设计可以把失败定位到决策机制，而不是仅判断一段自然语言“看起来是否不错”。

## 3. RAG 冻结评测集

数据文件：`evals/rag/careerpilot-rag-seed-v1.json`

每个 Case 使用独立 SQLite 数据库，先写入该 Case 的冻结文档，再调用生产代码中的分块、建索引与 `RagRetriever`。不调用网络，不依赖实时网页，也不使用外部模型。

| Case | 能力 | 主要成功条件 |
|---|---|---|
| R01 | 直接事实召回 | 正确文档被召回 |
| R02 | 领域过滤 | 同关键词的错误领域文档不进入结果 |
| R03 | 多查询、多来源 | 两份互补证据都被召回 |
| R04 | 图检索路径 | 关系型问题命中目标证据 |
| R05 | Parent-Child 上下文 | 局部命中可追溯到完整来源文档 |
| R06 | 无答案 | 冻结语料没有依据时返回空结果 |
| R07 | 用户隔离 | 只召回当前用户私有文档 |
| R08 | 时效性 | 当前资料被召回，过期资料被抑制 |

主要指标：

- Recall@K：期望文档中有多少进入结果；
- Precision@K：返回文档中有多少属于期望集合；
- MRR：第一个正确结果出现的位置；
- Pass Rate：满足该 Case 全部成功条件的比例；
- P50 延迟：单 Case 检索的中位耗时。

跨用户文档泄漏和运行异常属于硬失败。时效性错误属于质量失败，因为旧资料仍可作为对照证据，但不能被当作当前事实使用。

## 4. 记忆系统冻结评测集

数据文件：`evals/memory/careerpilot-memory-seed-v1.json`

每个 Case 同样使用独立数据库，通过生产代码中的 `MemoryService`、`MemoryWritePolicy` 和状态机运行。

| Case | 能力 | 主要成功条件 |
|---|---|---|
| M01 | 偏好召回 | 相关偏好进入上下文 |
| M02 | 目标召回 | 规划时召回职业目标 |
| M03 | 无关抑制 | 无词义关联时不强行召回 |
| M04 | 用户隔离 | 不读取其他用户记忆 |
| M05 | 敏感默认隐藏 | 未明确要求时不暴露敏感记忆 |
| M06 | 敏感明确召回 | 用户明确要求且用途允许时可召回 |
| M07 | 写入门控 | 短暂负面情绪不进入长期记忆 |
| M08 | 稳定信息写入 | 明确、持久的偏好被正确分类 |
| M09 | 更正与替代 | 新表述生效，旧记忆变为 `superseded` |
| M10 | 去重 | 重复写入只保留一个权威记录 |

除召回指标外，写入门控使用 Accuracy，状态更正与去重使用 Lifecycle Accuracy。跨用户泄漏、未授权敏感信息暴露、短暂负面表达被写入、运行异常属于硬失败。

## 5. 报告生成与判定原则

运行器：`src/careerpilot/evaluation/system_benchmark.py`

输出两种格式：

- JSON：供持续集成、版本对比和后续可视化使用；
- Markdown：供产品、研发和评测人员阅读。

报告不生成一个混合“总分”。原因是 RAG 召回质量与记忆隐私安全的业务含义不同。两套系统分别报告指标，硬失败独立列出，避免平均分掩盖安全问题。

## 6. 本轮基线结论的解释

当前基线中，记忆系统的 10 个种子 Case 全部通过；RAG 的 8 个 Case 中 7 个通过。失败项是 R08：新旧招聘截止日期都被召回，说明 `requires_freshness` 当前影响结果状态，却没有在召回或重排阶段抑制过期证据。

这不是“模型答错了一道题”，而是一个可定位的系统缺口：时效需求已经进入查询计划，但时间元数据还没有转化为排序或过滤规则。

## 7. 适用边界与后续扩展

本评测集是设计驱动的 MVP 种子集，不声称代表真实用户请求分布。后续应逐步加入：

1. 匿名化真实 Trace 中的 Good Case、Bad Case 和边界 Case；
2. 多次重复运行与版本间配对比较，减少偶然波动；
3. RAG 最终答案的忠实度、引用正确率和矛盾证据处理；
4. 更长跨会话链路，以及 LoCoMo、LongMemEval 等外部数据集的适配；
5. 工具故障、索引损坏、模型超时和状态变化等扰动条件。

新增 Case 必须记录来源、主要决策点、控制变量、期望结果和失败等级，并保持测试用户与数据库隔离。
