# CareerPilot 罗盘完整功能体系与跨模块联动设计

## 1. 设计意图

CareerPilot 保留现有的一级旅程与导航：`对话 → 罗盘 → 航程`。

本次不重命名罗盘、不取消独立页面，也不把罗盘改造成求职看板。目标是让罗盘从单一的“方向确认与航程入口”，恢复为持续更新的职业认知中心，帮助用户回答：

1. 我目前更了解自己哪些方面；
2. 我正在考虑哪些职业方向；
3. 每个方向下有哪些公司、业务和岗位分支；
4. 为什么考虑它，还有哪些问题没有答案；
5. 最近的对话和行动如何改变了我的判断；
6. 下一步应该验证什么，而不是立刻做出永久选择。

核心分工保持不变：

- **对话**负责表达、澄清和识别信息；
- **罗盘**负责组织画像、方向、分支、证据与变化；
- **航程**负责把一个验证点变成真实行动；
- **知识库**负责保存岗位、公司、行业、面经和学习资料。

## 2. 为什么需要调整

当前实现主要呈现方向名称、方向来源、加入罗盘和开始航程。虽然页面已有方向、假设和想法三类内容，但缺少可以支持长期职业判断的结构：

- “AI 产品经理”无法继续展开到腾讯混元、美团 Agent 或具体 JD；
- 用户看不到支持证据、反对证据、未知问题和最近变化；
- 兴趣、优势、环境偏好与现实约束没有形成可回看的职业画像；
- 对话中识别出的新信息没有在罗盘中及时、透明地体现；
- 航程结果没有形成可见的认知更新；
- 罗盘因此更像航程前的确认页，而不是独立且有长期价值的产品空间。

本设计也恢复了原 PRD 对罗盘的要求：方向卡应包含探索阶段、支持与反对证据、未知问题、最近变化和下一验证点。

## 3. 竞品研究结论

### 3.1 主要产品模式

1. **测评驱动：CareerExplorer、PathwayU、学职平台**
   - 从兴趣、价值观、人格、工作环境偏好形成画像，再推荐职业；
   - 优点是画像完整，缺点是容易形成一次性、静态的测评结论。

2. **目标驱动：LinkedIn Career Insights、SeekOut Career Compass**
   - 先设置目标岗位，再汇集技能、地点、工作方式、发展目标、机会、人脉与学习建议；
   - 优点是信息与目标强关联，最适合罗盘主体。

3. **对话驱动：Indeed Career Scout**
   - 从个人资料、对话和持续反馈理解技能、兴趣与目标；
   - 适合 CareerPilot 的对话入口和右侧栏，但对话不能替代持久的罗盘空间。

4. **执行驱动：Teal、Huntr**
   - 以目标、申请阶段、活动、提醒和进度为核心；
   - 更适合航程，不应把罗盘变成任务或申请管理器。

### 3.2 CareerPilot 的差异化机会

CareerPilot 不复制“做一次测评得到推荐”，也不复制“维护一个求职看板”。罗盘的差异化是：从自然对话、用户材料和真实行动中持续形成职业认识，同时保留来源、不确定性、反证和变化过程。

参考来源：

- [CareerExplorer](https://www.careerexplorer.com/faqs/assessment-science/why-am-i-given-different-scores/)：职业兼容性由兴趣、工作环境、薪资、需求与培训成本等多维因素解释；
- [PathwayU](https://blog.pathwayu.com/a-pro-tip-for-pathwayu-learners-start-buidling-your-social-capital)：兴趣、价值观、人格与工作环境偏好共同构成画像，并鼓励通过职业信息和从业者访谈继续验证；
- [LinkedIn Career Insights](https://www.linkedin.com/help/linkedin/answer/a6217425)：围绕目标岗位组织公司、人脉、课程和计划；
- [SeekOut Career Compass](https://support.seekout.com/en/articles/11877947-career-compass-profile)：区分已有技能与想发展技能，并记录角色、地点、远程、管理倾向和 North Star；
- [Indeed Career Scout](https://www.indeed.com/help/job-seekers/articles/33940519874317-what-is-indeed-career-scout)：从资料、对话和交互中持续个性化职业建议；
- [学职平台](https://xz.chsi.com.cn/home.action?menu_id=600)：把职业定义、职责、工作环境、发展路径和典型一天组合为职业世界信息。

## 4. 方案比较

### 方案 A：扩展当前方向卡体系（已选）

保留方向卡作为视觉与交互中心，在卡片外围补充职业画像、方向对比、变化时间线和待确认观察；具体证据与详情通过抽屉或展开层呈现。

- 优点：延续现有罗盘语义、页面设计和用户习惯；信息全面但仍有清晰焦点；可以渐进实现。
- 代价：需要重构方向、分支和证据的数据模型，不能只改前端展示。

### 方案 B：综合仪表盘

用多个数据面板同时展示画像、方向、技能、任务和进度。

- 优点：信息密度高；适合成熟职业管理工具。
- 代价：容易制造压力并削弱 CareerPilot 的陪伴感，也会与首页和航程重复。

### 方案 C：职业知识图谱或无限画布

把方向、技能、公司和证据表示为节点关系图。

- 优点：关系表达强。
- 代价：学习成本、移动端复杂度和维护成本过高，用户很难迅速找到当前重点。

选择方案 A。罗盘保持方向卡中心结构，复杂度通过渐进展示控制。

## 5. 罗盘功能体系

### 5.1 罗盘概览

页面首屏提供一段低负担摘要：

- 当前重点方向数量；
- 最近新增或变化的内容；
- 当前最值得回答的一个问题；
- 是否存在待用户确认的 AI 推断。

概览不显示完成率，不用“你还差多少”制造压力。

### 5.2 我的职业画像

职业画像是方向判断的背景层，不取代方向卡。首版包含五个维度：

1. **兴趣与投入**：用户愿意持续靠近的主题、问题和工作内容；
2. **优势与证据**：用户做得较好且有经历或成果支持的能力；
3. **工作环境偏好**：节奏、协作方式、稳定性、自主度、组织类型；
4. **价值与取舍**：成长、收入、影响、稳定、地点等当前在意因素；
5. **现实约束与风险**：地点、时间、学历、求职周期、精力和反复出现的阻碍。

每条画像必须显示其性质：

- 用户明确表达；
- 从真实经历归纳并经用户确认；
- AI 待确认观察。

画像默认只展示每个维度最重要的 1–3 条，完整内容按需展开。用户可以编辑、否认、暂停使用或查看来源。

### 5.3 重点方向

同屏最多展示三个活跃方向，方向示例为“AI 产品经理”“新能源产品经理”“国企产品运营”。更多方向进入“暂时放下”或历史列表。

每张方向卡默认显示：

- 方向名称；
- 当前探索阶段；
- 一句“为什么它在这里”；
- 当前最关键的未知问题；
- 最近一次变化；
- 下一验证点；
- 目标分支数量；
- 关联航程状态。

方向状态使用自然语言：

- 刚刚注意到；
- 正在了解；
- 正在验证；
- 重点投入；
- 暂时放下；
- 已经排除。

状态不是匹配分数，也不代表系统替用户做出决定。

### 5.4 目标分支

一个职业方向可以包含多个目标分支：

```text
AI 产品经理
├─ 通用探索
├─ 腾讯｜混元｜大模型平台产品
├─ 美团｜Agent｜本地生活场景
└─ 某公司｜具体 JD
```

分支字段包括：

- 公司；
- 业务方向或部门；
- 岗位名称；
- 地点、招聘类型和资历层级；
- JD 或来源链接；
- 与方向共性相比的差异要求；
- 当前优先级与状态；
- 关联的岗位、资料和航程。

方向共性信息只保存一次；公司、业务或 JD 特有内容保存在分支中。没有具体目标时保留“通用探索”，不强迫用户过早选择公司。

### 5.5 判断依据

方向和分支详情都包含四类判断信息：

1. **支持证据**：用户表达、项目经历、行动结果或可信外部资料；
2. **反对证据**：不喜欢的工作内容、现实限制、行动后的负面反馈；
3. **未知问题**：当前没有足够信息回答的关键问题；
4. **AI 的理解**：系统基于现有内容提出、但尚未被用户确认的解释。

所有证据保留来源类型、原始事件、时间和关联对象。点击证据打开右侧抽屉，不在卡面铺满引用。

不显示伪精确匹配度。可使用“证据较少 / 初步有依据 / 已有多次真实验证”等文字，但必须解释原因。

### 5.6 职业世界信息

方向详情提供与职业判断直接相关的现实信息：

- 典型工作内容；
- 工作中的一天；
- 常见业务场景；
- 核心能力与进入门槛；
- 常见发展与转岗路径；
- 市场需求、薪资与地点分布；
- 代表公司和业务类型。

这部分从知识库读取并显示来源与更新时间。它不是百科全书：默认只展示与用户当前问题相关的信息。

### 5.7 方向对比

用户可选择 2–3 个方向或分支进行对比。对比维度来自用户当前画像与现实资料，而不是固定模板：

- 兴趣与工作内容；
- 已有优势和待补能力；
- 环境偏好与现实工作方式；
- 地点、时间和进入成本；
- 市场机会；
- 支持证据、反证和未知项；
- 当前最小验证成本。

对比结果不宣布唯一最佳方向，只突出“差异最大之处”和“最值得先验证的问题”。

### 5.8 下一验证点

每个活跃方向只突出一个下一验证点，例如：

- 确认自己是否喜欢长期处理模糊需求；
- 了解平台型 AI 产品与场景型 AI 产品的日常差异；
- 验证自己是否能接受目标团队的工作节奏。

验证点可以来自未知问题、矛盾证据或最近变化。点击后生成一张行动草案；只有用户确认进入航程后才创建正式任务。

### 5.9 变化时间线与复盘

时间线回答“当时怎么想、后来发生了什么、现在为什么变化”。记录：

- 新方向或分支出现；
- 用户修改画像或约束；
- 证据加入、被否认或失效；
- 方向状态改变；
- 航程行动完成并产生新发现；
- 用户暂停、排除或重新拾起方向。

系统可以提出“方向更新建议”，但暂停、排除、重点投入等高影响变化仍由用户决定。

### 5.10 想法与待确认观察

保留现有想法区域，但调整其角色：

- 想法是尚未结构化的信号池；
- AI 可以建议它与某个画像维度、方向或分支有关；
- 明确表达可直接形成方向信息；
- 推断关系必须经用户确认；
- 想法不会自动生成航程任务。

待确认观察集中展示，避免散落在每张方向卡上反复打断用户。

## 6. 页面信息架构

```text
罗盘
├─ 首屏：罗盘概览
│  ├─ 当前重点
│  ├─ 最近变化
│  └─ 一个关键问题
├─ 主体：重点方向卡（最多 3 张）
│  ├─ 方向摘要
│  ├─ 目标分支
│  ├─ 判断依据
│  ├─ 职业世界
│  ├─ 下一验证点
│  └─ 关联航程
├─ 辅助入口
│  ├─ 我的职业画像
│  ├─ 方向对比
│  ├─ 变化时间线
│  └─ 待确认观察
└─ 下段：想法收藏
```

方向卡仍是首屏视觉中心。职业画像、比较和时间线通过辅助入口或抽屉进入，避免退化成密集仪表盘。想法收藏保留当前页面的第二章节关系。

## 7. 跨页面信息流

### 7.1 对话 → 罗盘

对话识别以下信息：

- 职业方向；
- 公司；
- 业务方向或部门；
- 具体岗位或 JD；
- 地点、资历、招聘类型等硬约束；
- 兴趣、优势、环境偏好和价值取舍；
- 用户明确的否定或变化。

写入规则：

- 用户明确表达的信息自动写入罗盘，并在对话右侧栏显示“刚刚更新”；
- AI 推断、冲突信息和高影响状态变化进入待确认观察；
- 用户可以立即撤销、编辑或查看来源；
- 对话结束后罗盘可见更新，不要求用户再次完成形式化确认。

### 7.2 罗盘 → 航程

- 罗盘选择一个方向或分支及其下一验证点；
- 系统生成行动草案，说明要验证什么、建议行动、预计投入和完成后要回答的问题；
- 用户确认后才创建或更新航程；
- 航程按方向共性与分支差异生成任务，避免不同公司重复通用任务。

### 7.3 航程 → 罗盘

航程完成后收集一句轻量反思，形成：

- 新支持证据；
- 新反对证据；
- 已回答或新增的未知问题；
- 画像更新建议；
- 方向状态更新建议。

低风险的事实结果可以直接回流；涉及偏好解释、方向优先级、暂停或排除的变化必须由用户确认。

### 7.4 知识库 → 罗盘

知识库为职业世界、公司和 JD 信息提供来源。资料更新不直接改变用户判断，只更新现实信息并提示：

- 哪条信息发生变化；
- 更新时间和来源；
- 是否可能影响当前方向或分支。

## 8. 对话右侧栏与罗盘的关系

对话右侧栏不是迷你罗盘，而是当前对话的即时反馈面板。它只展示：

- 本轮识别到的方向、公司、业务和约束；
- 刚刚自动更新到罗盘的内容；
- 待确认的 AI 推断；
- 与当前内容最相关的一个罗盘入口。

完整画像、证据、比较、时间线和方向管理仍在罗盘完成。

## 9. 状态与自动化边界

### 9.1 可自动写入

- “我决定投 AI 产品经理”中的职业方向；
- “我想看腾讯混元”中的公司与业务；
- 用户提供或明确指向的具体 JD；
- “我不考虑异地”“我更想要稳定环境”等直接表达；
- 已发生的航程结果和用户原话。

### 9.2 必须确认

- AI 推断的兴趣、优势、价值观和风险；
- 将一个想法正式关联到某个方向；
- 把方向设为重点投入、暂停或排除；
- 将新发现解释为支持或反对某方向；
- 开始航程或创建外部任务；
- 合并两个可能重复但含义不确定的方向或分支。

所有自动更新都可撤销、编辑并查看来源。

## 10. 首版范围

### 必须实现

1. 对话识别并自动写入明确方向、公司、业务、岗位和约束；
2. 方向与目标分支数据模型；
3. 增强方向卡：状态、理由、未知问题、最近变化、下一验证点；
4. 支持证据、反对证据和来源抽屉；
5. 职业画像摘要；
6. 2–3 个方向或分支的基础对比；
7. 航程结果回流为证据或更新建议；
8. 对话右侧栏显示本轮罗盘更新与撤销入口。

### 后续增强

- 完整职业世界数据与趋势；
- 方向变化时间线的高级筛选；
- 人脉、从业者和信息访谈建议；
- 更丰富的技能证据与作品关联；
- 定期 Navigation Review；
- 基于多次行动的长期模式总结。

### 明确不做

- 强制长测评；
- 单一匹配百分比或雷达图；
- 自动宣布最适合的职业；
- 复杂知识图谱或无限画布；
- 在罗盘内复制聊天、任务管理或完整知识库；
- 因一次对话或一次失败行动自动排除方向；
- 用申请数量或完成率评价用户。

## 11. 内容与视觉原则

- 延续现有暖色、毛玻璃、方向卡和沉浸式空间语言；
- 首屏只强调一个主问题和最多三个方向；
- 复杂信息通过抽屉、展开与二级视图渐进披露；
- 事实、用户表达、AI 推断和外部资料有清晰标签；
- 不依赖颜色表达状态；
- 移动端将方向卡横滑，详情使用底部抽屉；
- 尊重减少动态效果设置；
- 空状态引导用户从对话开始，不伪造画像或方向。

## 12. 成功标准

定性上，用户进入罗盘后应能在较短时间内回答：

- 我当前最关注什么方向；
- 它下面有哪些具体目标；
- 我为什么考虑它；
- 哪些判断是事实，哪些仍是猜测；
- 最近发生了什么变化；
- 下一步需要验证什么。

产品指标应关注：

- 对话识别结果被撤销或纠正的比例；
- 用户是否会回看方向证据与变化；
- 下一验证点转化为航程的比例；
- 航程完成后是否产生有效的新证据；
- 用户是否会暂停、恢复或调整方向，而不是只新增不管理；
- 多个方向并存时，用户是否能完成有依据的比较。

不以罗盘打开次数、方向数量或任务完成率单独判断成功。

## 13. 验收标准

- 产品仍保持“对话—罗盘—航程”一级结构；
- 罗盘仍以方向卡为核心，而不是仪表盘、聊天页或任务看板；
- 用户明确表达的方向、公司和业务可在一次成功对话后自动出现在罗盘；
- AI 推断不会伪装成用户事实；
- “AI 产品经理”可以包含多个公司、业务和 JD 分支；
- 每个方向至少能展示理由、未知问题、最近变化和下一验证点；
- 用户能查看支持证据、反对证据及其来源；
- 职业画像与方向相关，但不会压过方向卡成为首屏主体；
- 用户可以比较 2–3 个方向或分支，但系统不宣布唯一答案；
- 开始航程仍需用户明确确认；
- 航程完成后结果能够回到罗盘，形成可见的认知更新；
- 原有想法收藏继续存在，并作为方向形成的信号池；
- 页面在桌面、移动端和减少动态模式下均可完整使用。

## 14. 实现边界与数据契约

以下决定用于消除实施阶段会影响架构与验收的歧义。它们是本设计的默认实现约束，不要求用户再做产品选择。

### 14.1 与既有设计和数据的关系

本设计扩展而不是推翻现有 `directions`、`direction_signals`、`hypotheses`、`ideas`、`journeys` 和 `journey_tasks`：

- 现有 confirmed direction 原样保留，补充新的详情与状态字段；
- 现有 direction label 不包含可可靠拆分的公司或业务时，不自动猜测分支；
- 已明确包含公司和岗位的方向，可在后台迁移为“职业方向 + 一个目标分支”，同时保留原始 label 和来源；
- hypotheses 映射为待确认观察或方向证据建议，不自动变成用户画像事实；
- ideas 继续作为独立对象，只增加建议关联与确认关联；
- Dreaming 内容继续作为观察来源，不直接改变方向状态；
- 现有前端与 API 在迁移期保持兼容，新字段采用增量返回；
- 数据库迁移只新增表、字段和索引，不破坏性重写历史记录。

若本设计与 `2026-10-25-careerpilot-compass-page-design.md` 的确认规则冲突，以本设计为准：用户明确表达的低风险方向信息自动写入；AI 推断和高影响状态变化仍需确认。原有视觉语言、方向卡中心结构和想法章节继续沿用。

### 14.2 对话提交时点与一致性

罗盘提取可以在回复生成过程中准备，但只在一次对话轮次成功完成后提交。失败、取消或空回复不产生方向更新。

一次对话产生的结构化更新作为一个幂等 `compass_update_batch` 提交，至少包含：

- owner 与 run / conversation / message 标识；
- 原文引用；
- 字段类型与结构化值；
- explicit 或 inferred；
- 置信度与简短理由；
- 目标方向或分支标识；
- 创建时间和提交状态。

同一 run 只能提交一次有效批次。批次中的数据库写入应使用同一事务：要么方向、分支、来源事件与更新日志全部成功，要么全部回滚。知识收集等外部后台工作不属于该事务；其入队失败时保留罗盘更新并明确显示“资料收集暂不可用”，允许重试。

### 14.3 明确表达与推断的机器契约

每个提取字段必须带原文引用，不能只返回总结。首版可以自动写入的 explicit 类型限定为：

- 用户使用“我想、我决定、我要投、我不考虑、我更在意、我只能”等第一人称明确表达；
- 用户主动提供的公司、业务、岗位、JD、地点、资历或招聘类型；
- 用户对已有信息的直接纠正或否定；
- 已完成行动的确定性结果和用户原话。

以下一律视为 inferred：

- 从情绪、语气或单次行为推断兴趣和价值观；
- 将能力表现解释为稳定优势；
- 把某次失败解释为不适合某方向；
- 在缺少明确词语时推断公司、部门、岗位层级或优先级；
- 推断用户准备重点投入、暂停或排除方向。

服务端校验字段类型、引用是否来自本轮用户消息、值的长度和允许的状态变化。模型给出 explicit 但不符合上述白名单时，降级为 inferred。

### 14.4 撤销与纠正

自动写入不直接删除历史，而通过更新事件和当前投影实现：

- 对话右侧栏将本轮更新按批次展示，用户可以逐项纠正，也可以撤销整批；
- 撤销创建反向事件，并恢复更新前投影，不删除原始消息、来源引用或审计记录；
- 当前会话中始终可撤销最近一次自动更新；离开页面后仍可在罗盘“最近变化”中撤销尚未被后续用户编辑覆盖的更新；
- 一旦某字段被用户再次手动编辑，旧批次不能整体回滚覆盖新值，只能逐项纠正；
- 撤销方向创建时，如果该方向已被用户用于创建航程，不级联删除航程，而改为提示用户分别处理。

### 14.5 方向、分支与 JD 判重

方向身份使用规范化职业族与角色名称，不以展示文案作为唯一键。目标分支身份由以下组合决定：

```text
owner + direction + normalized company + normalized business + normalized role
```

- 同公司、同业务、同角色的不同写法优先合并为同一分支；
- 业务或角色无法可靠判断相同时保留两个候选，并提出合并建议；
- 具体 JD 作为分支下的目标岗位记录，不直接等于分支；
- 同一来源 URL 的 JD 更新保存为新版本；
- 不同 URL 但公司、岗位和发布时间高度一致时可以建议合并，不能静默覆盖；
- 用户确认的手动合并保留别名和所有来源。

### 14.6 方向摘要字段的生成与刷新

“为什么它在这里、未知问题、最近变化、下一验证点”作为有版本的派生摘要持久化，不在每次页面渲染时实时生成。

刷新触发条件：

- 成功提交一批相关对话更新；
- 用户确认或否认证据；
- 航程完成并提交反思；
- 可信职业资料发生可能影响判断的变化；
- 用户主动要求重新整理。

摘要由后台整理任务生成并引用输入事件版本。新摘要生成失败时继续显示上个版本并标记更新时间。摘要是“泊泊的整理”，用户可以纠正；纠正后的用户文本优先展示，除非用户主动要求重新生成。系统不能用新摘要自动改变重点投入、暂停或排除状态。

### 14.7 三个重点方向的含义

“最多三个”是首屏重点展示规则，不是数据保存上限：

- 用户可以保存更多方向；
- 最多三个方向可被标记为重点；
- 新增第四个方向不会自动挤掉旧方向，而是进入“其他方向”；
- 用户尝试将第四个方向设为重点时，需要选择一个现有重点方向移出；
- 移出重点不等于暂停或排除，只改变展示优先级。

### 14.8 罗盘与航程的首版契约

罗盘交给航程的行动草案至少包含：

- direction_id；
- branch_id（可空）；
- verification_question；
- suggested_action；
- rationale；
- estimated_minutes 或投入级别；
- completion_prompt；
- supporting_source_ids；
- draft_version。

用户在航程确认后才生成正式任务。航程完成时返回：

- action_id 与关联方向 / 分支；
- completion fact；
- 用户的一句反思；
- 可选的结果分类：支持、反对、仍未知、新问题；
- 相关附件或来源。

完成事实与用户原话可以自动成为来源事件；“它支持或反对哪个方向”的解释默认是待确认建议。用户在完成反馈中主动选择“更想继续 / 不太适合 / 还不确定”时，该选择可直接成为用户确认的证据，但仍不自动暂停或排除方向。

### 14.9 首版方向对比

首版采用固定基础维度，按用户画像调整排序，不由模型每次自由生成结构：

- 主要工作内容；
- 已有证据与能力；
- 待补能力或进入成本；
- 工作环境与现实约束；
- 市场机会；
- 最大未知项；
- 最小验证行动。

可以比较多个职业方向，或比较同一方向下的多个目标分支；首版不混合比较一个宽泛方向与另一个方向下的具体 JD。缺失内容明确显示“还不知道”，不推断补齐。AI 可以在固定维度之外补充一条“本次差异最大之处”，但必须引用已有数据。

### 14.10 首版职业世界信息

首版读取现有知识库和已收集岗位中的可信资料，并在方向、目标分支或航程发生有效变化时及时触发相应资料的后台补充或刷新；展示内容必须带有来源时间，没有资料时显示诚实空状态，不生成无来源职业事实。

这里的“及时更新”只覆盖用户当前正在探索或准备的上下文，不做全库持续爬取。完整职业百科、市场趋势监控和全局定时刷新属于后续增强。首版预留方向与资料的关联字段，但不要求一次建成新的职业数据平台。

## 15. 对话模块更新设计

### 15.1 对话的职责

对话既是自然语言入口，也是罗盘信息的主要采集入口，但不成为第二个罗盘或航程编辑器。它负责：

- 识别用户明确表达的方向、公司、业务、岗位、约束和偏好；
- 发现可能需要确认的画像、证据和方向变化；
- 用自然语言帮助用户澄清层级关系；
- 展示本轮对罗盘造成的结构化更新；
- 在用户希望行动时生成航程草案；
- 在用户上传或引用资料时建立知识关联建议。

### 15.2 结构化识别结果

对话运行结果除普通回复外，可以携带一个 `compass_update_batch`：

```text
CompassUpdateBatch
- id
- run_id
- direction_updates[]
- branch_updates[]
- profile_updates[]
- constraint_updates[]
- evidence_suggestions[]
- knowledge_link_suggestions[]
- explicitness per item
- source_quote per item
- committed_at?
```

示例：用户说“我准备重点看看腾讯混元的 AI 产品经理，最好在深圳，不考虑纯运营岗。”

```text
职业方向：AI 产品经理                  explicit
公司：腾讯                            explicit
业务：混元 / 大模型                   explicit
地点偏好：深圳                        explicit
排除条件：纯运营岗位                  explicit
方向状态：重点投入                    inferred，需确认
```

系统自动保存前五项；最后一项只能在右侧栏提出确认，不能因为“重点看看”就自动修改高影响状态。

### 15.3 对话右侧栏

右侧栏从当前的 Dreaming / hypothesis 摘要升级为三层、随当前对话变化的上下文栏：

1. **本轮刚刚理解**
   - 展示新识别或修改的字段；
   - 标明“已自动更新”或“等待确认”；
   - 支持逐项纠正、撤销整批和查看原话。

2. **当前关联目标**
   - 当前方向；
   - 当前公司 / 业务 / JD 分支；
   - 相关航程及分支状态；
   - 与本轮最相关的资料数量或收集状态。

3. **一个下一入口**
   - 信息仍模糊：继续聊清楚；
   - 已形成方向：去罗盘查看；
   - 用户明确想行动：预览航程草案；
   - 用户正在执行：返回对应航程分支。

右侧栏不展示完整证据、方向比较、任务列表或知识列表。移动端使用可展开的“本轮理解”底部面板，不直接隐藏这些反馈。

### 15.4 对话中的歧义处理

- 公司明确、方向不明确：只有当当前对话上下文已经绑定一个明确方向，或本轮上传的 JD 同时给出可归一化角色时，才自动关联；否则保存公司兴趣线索，追问其关注的岗位或业务，不直接创建职业方向；
- 方向明确、公司不明确：创建或更新通用方向，不强迫选择公司；
- 公司与业务明确、岗位模糊：若当前对话已绑定方向，则继承父方向的角色族并创建正式目标分支；若没有方向上下文，则只创建独立的 `target_candidate`，不触发分支摘要、航程或分支资料收集，补充方向后再转为正式分支；
- 用户贴入 JD：优先从 JD 识别公司、业务、岗位、地点和要求，并让用户看到提取结果；
- 新信息与现有分支冲突：保留两个版本或提出纠正，不静默覆盖；
- 一句话涉及多个方向：可以创建多个方向更新，但右侧栏按用户表达顺序展示，不替用户判断优先级。

这里的“当前对话已绑定方向”指：用户从某张方向卡、分支或航程深链进入对话，或当前连续话题中最近一次用户或泊泊明确提及该方向且尚未切换主题。不能仅因为账户中只存在一个活跃方向就自动关联。存在多个可能方向、主题已经切换或上下文指针失效时，必须把关联作为待确认项。

### 15.5 对话到航程的控制边界

以下表达只更新罗盘，不自动创建行动：

- “我想做 AI 产品经理”；
- “我最近在看腾讯混元”；
- “我觉得 Agent 方向也不错”。

以下表达可以生成航程草案，但仍需要用户确认：

- “帮我开始准备腾讯混元的岗位”；
- “给我安排一个验证 AI 产品经理是否适合我的计划”；
- “把这份 JD 拆成下一步”。

用户确认草案后，对话返回明确结果：“已加入 AI 产品经理航程的腾讯｜混元分支”，并提供进入该分支的入口。

## 16. 航程分支体系

### 16.1 核心模型

一个职业方向对应一段长期航程，航程内部包含一条通用主线和零到多个目标分支：

```text
AI 产品经理航程
├─ 通用主线
│  ├─ 了解 AI 产品岗位类型
│  ├─ 整理通用项目证据
│  └─ 补充 AI 产品基础能力
├─ 腾讯｜混元分支
│  ├─ 拆解具体 JD
│  ├─ 了解平台型产品工作
│  └─ 准备腾讯相关面试证据
└─ 美团｜Agent 分支
   ├─ 理解本地生活 Agent 场景
   └─ 准备场景落地案例
```

同一方向新增公司、业务或 JD 时，不重复创建新的方向航程，而是在已有航程下新增或复用目标分支。

### 16.2 航程分支类型

```text
JourneyBranch
- id
- journey_id
- compass_branch_id?       # 通用主线为空
- kind: common | target
- title
- status: draft | active | paused | completed | archived
- priority
- rationale
- focus_action_id?
- created_at
- updated_at
```

- 每段方向航程恰好有一条 `common` 主线；
- 每个罗盘目标分支最多关联一个未归档的 `target` 航程分支；
- 一个具体 JD 是目标分支下的岗位记录，可以影响任务，但不会为每份 JD 创建新航程分支；
- 首版不支持为单份 JD 建立第二层航程分支。高优先级 JD 通过 `target_job_id` 关联分支行动；需要独立申请流程时仍在同一目标分支内组织，后续再评估是否引入独立的申请对象。

### 16.3 行动归属

每个行动增加：

```text
- journey_branch_id
- scope: common | branch_specific
- target_job_id?
```

- 通用行动只存在于主线并可被所有目标分支引用；
- 分支行动记录公司、业务或 JD 的差异要求；
- 新增目标分支时，已完成通用行动显示为“已具备的共同基础”，不复制任务；
- 目标分支视图通过同一 `journey_id` 动态包含通用主线行动，不创建额外引用记录或内容副本；
- 一个行动只拥有一个实际状态，避免主线完成、分支仍显示未完成的冲突。

### 16.4 分支创建与变化

创建分支的来源包括：

- 罗盘目标分支点击“开始准备”；
- 对话中的用户明确请求并确认行动草案；
- 从岗位详情点击“加入航程”；

创建规则：

1. 查找所属方向的现有航程，没有时创建一段方向航程和通用主线；
2. 查找对应罗盘目标分支，没有时先创建或确认目标分支；
3. 复用现有未归档航程分支；
4. 只生成与该公司、业务或 JD 差异相关的行动；
5. 展示将复用的通用基础和新增的分支行动；
6. 用户确认后提交。

当罗盘新增一个明确目标分支，而该方向已经存在航程时，系统可以自动创建一个无任务的 `draft` 航程分支占位，使其出现在分支选择器中并标记“尚未开始准备”。这不生成行动、不启动资料准备收集，也不改变焦点分支。用户点击“开始准备”并确认差异行动草案后，分支才进入 `active` 并创建任务。若方向尚未开始航程，只保存罗盘目标分支；首次创建方向航程时再为已选择的目标分支创建 draft 或 active 分支。

罗盘分支被暂停时，航程分支提出同步暂停建议，但不自动中断正在进行的面试或有明确截止时间的行动。罗盘分支归档也不删除航程历史和足迹。

### 16.5 航程页面结构

保留现有 `路径 / 日历 / 足迹` 三个视图。在路径视图的航程选择下增加分支选择：

```text
AI 产品经理航程
[综合路径] [通用主线] [腾讯｜混元] [美团｜Agent]
```

- **综合路径**：显示当前焦点行动、通用主线与各活跃分支的最近节点；
- **通用主线**：只显示共性行动；
- **目标分支**：显示共性基础摘要和该分支的差异行动；
- 切换分支不改变任务状态；
- 用户主动选择的分支成为当前聚焦分支，不由系统进入页面时自动抢焦点；
- 日历和足迹默认聚合所有分支，可按航程分支筛选。

首屏仍然只突出一个当前行动。若多个分支都有临近节点，系统按明确截止时间、用户主动聚焦和已开始状态排序，并说明该行动属于哪个分支。

### 16.6 分支状态与焦点

- 一段方向航程可以有多个 active 分支；
- 每个分支可以有自己的 `focus_action_id`；
- 整段航程另有一个 `focused_branch_id`，决定路径首屏默认展示；
- 综合路径的主行动来自 focused branch；
- 有更紧急的其他分支节点时只显示时间提醒，不自动切换 focused branch；
- 暂停分支不会暂停通用主线；
- 完成目标分支代表该目标阶段结束，不代表职业方向已经验证完成。

### 16.7 航程回流罗盘

完成行动后，回流对象必须精确到方向或分支：

- 通用行动结果进入职业方向证据；
- 公司 / 业务差异行动进入目标分支证据；
- 针对具体 JD 的准备结果关联目标岗位；
- 同一结果可以同时支持方向和分支，但需要分别说明理由；
- 用户原话与完成事实自动保存，AI 的支持 / 反对解释进入待确认建议。

## 17. 知识库更新设计

### 17.1 保留现有知识分类

知识库仍按内容域组织：

- 个人资料；
- 岗位信息；
- 往年题目与面经；
- 学习资源。

不新增“腾讯混元资料库”这类一级分类。方向与分支只作为后台关联、更新调度和跨模块取用的上下文，不成为知识库前端的新分类或主要操作维度，避免知识体系和页面复杂度随目标数量增长。

### 17.2 方向与分支关联

一个知识对象只保存一份规范记录，通过关系表关联多个上下文：

```text
KnowledgeContextLink
- id
- resource_type
- resource_id
- direction_id?
- compass_branch_id?
- journey_id?
- journey_branch_id?
- target_job_id?
- purpose: explore | compare | prepare | interview | learn | evidence
- relevance_reason
- source: user | system | collection_job
- confirmed
- created_at
```

- 同一份通用 AI 产品指南可以关联多个公司分支，但不复制内容；
- 一份腾讯混元 JD 关联 AI 产品经理方向、腾讯混元分支和对应岗位；
- 一份美团 Agent 面经只默认进入美团分支，不污染其他分支；
- 用户可以修改或删除关联，不影响知识对象本身；
- AI 推断的关联先标记为 suggested，用户明确要求收集的资料可直接建立 confirmed 关联。

### 17.3 保留原有知识库前端

知识库首版不新增方向筛选条、分支标签、航程入口或新的详情层级，继续使用现有分类、搜索、资料卡和详情呈现。用户直接进入知识库时，看到的导航方式和主要操作与现在一致。

方向、分支、航程和具体 JD 的关联保存在后台，不要求用户先理解这些关系才能管理资料。罗盘和航程需要资料时，由各自页面展示少量相关摘要或引用；用户进入知识库后仍回到对应的原有内容分类，而不是进入一套新的“方向知识库”界面。

首版允许在不改变布局的前提下复用已有状态表达，例如资料更新时间、采集状态或失效状态；不为关联关系增加新的常驻控件。若未来数据量证明用户确实需要按目标筛选，再单独验证该需求，而不是在本次联动中预埋复杂前端。

### 17.4 及时、上下文化的资料更新

知识收集任务增加可选的方向分支和航程分支上下文：

```text
CollectionJob
- direction_id
- compass_branch_id?
- journey_id?
- journey_branch_id?
- purpose
- normalized_query_key
- query
- status
- result_count
- last_verified_at
```

触发规则：

- 明确职业方向成功写入罗盘：立即创建或刷新方向级岗位画像和现实机会任务；
- 明确公司 / 业务分支成功写入罗盘：立即创建或刷新该分支的公司、业务和岗位证据任务；
- 目标分支在航程中激活：立即补充该分支相关面经、往年题目和学习资源；
- 具体 JD 加入航程：优先保存和解析该 JD，不自动无限扩展搜索；
- 航程产生新的验证问题或资料缺口：只补充对应方向、分支或 JD 的资料；
- 用户从现有知识库入口发起刷新或采集：沿用原有前端流程，后台结合入口来源和已知上下文缩小范围，不刷新所有方向。

去重键至少包含 owner、purpose、规范化方向、公司、业务、岗位和主要约束。方向级通用资料与分支专属资料使用不同键。

更新任务异步执行，不阻塞对话回复、罗盘写入或航程激活。相同上下文已有进行中任务时复用该任务；已有结果仍在有效期内时直接复用并记录检查时间。更新完成后写入原有知识分类，并通过 `KnowledgeContextLink` 供罗盘和航程准确取用，不额外生成一套前端内容副本。

### 17.5 资料推荐边界

- 罗盘只显示能帮助判断方向的少量资料与事实摘要；
- 航程只显示当前行动需要使用的资料；
- 知识库保存完整记录、来源、版本和关联；
- 对话可以搜索和解释资料，但不会把所有聊天引用自动永久保存；
- 没有可靠来源时显示“尚未找到可信资料”，不能用模型常识填充公司或岗位事实。

### 17.6 资料生命周期

- JD 更新保存版本并提示关联分支；
- 岗位过期后保留历史与用户足迹，但不继续作为活跃机会推荐；
- 来源失效时保留关联并标记不可用；
- 方向或分支暂停不会删除资料，只影响默认推荐；
- 方向或分支合并时合并关联关系并保留来源；
- 用户删除私人资料时，相关引用进入不可用状态，不保留可恢复正文副本。

## 18. 跨模块状态所有权

为避免四个页面互相覆盖数据，状态所有权如下：

| 对象 | 唯一权威模块 | 其他模块可以做什么 |
|---|---|---|
| 用户原话、对话提取批次 | 对话服务 | 罗盘查看来源、撤销投影 |
| 职业画像、方向、目标分支 | 罗盘 | 对话提出更新；航程回传证据 |
| 航程分支、行动、日历、足迹 | 航程 | 罗盘提出验证点；对话生成草案 |
| 资料正文、来源、版本、可信度 | 知识库 | 其他模块触发定向更新并建立引用 |
| 支持 / 反对证据关系 | 罗盘 | 航程和对话提出建议 |
| 外部写入及回执 | 动作服务 | 航程和对话发起预览 |

任何跨模块操作都先写入权威对象，再通过关系 ID 展示，不在多个模块复制一份可独立编辑的数据。

## 19. 端到端用户旅程示例

### 场景一：只有通用方向

1. 用户在对话中说“我想试试 AI 产品经理”；
2. 对话识别明确方向，成功回复后自动写入罗盘；
3. 右侧栏显示“已加入罗盘：AI 产品经理”，支持撤销；
4. 罗盘出现通用方向卡和一个未知问题；
5. 用户选择下一验证点并确认开始航程；
6. 系统创建 AI 产品经理航程与通用主线；
7. 知识库开始收集方向级岗位画像和可信机会。

### 场景二：增加具体公司和业务

1. 用户后来在对话中说“我更想看腾讯混元”；
2. 系统识别公司与业务，并关联到已有 AI 产品经理方向；
3. 罗盘新增“腾讯｜混元”目标分支；
4. 已有通用航程不重建，航程内出现无任务的腾讯混元 draft 分支；
5. 用户确认“开始准备”后，分支激活；通用行动继续复用，只新增平台型产品、腾讯 JD 和面试准备等差异行动；
6. 知识库在罗盘阶段收集公司、业务和岗位证据，在分支激活后再收集面经与准备资料。

### 场景三：加入另一业务分支

1. 用户上传美团 Agent JD；
2. 对话右侧栏展示提取出的公司、业务、岗位和地点；
3. 明确信息自动写入，美团 Agent 成为同一方向下的新分支；
4. 罗盘支持比较腾讯混元与美团 Agent；
5. 若方向航程已存在，航程显示未启动的美团 draft 分支；用户确认准备后才生成差异行动，并且不复制已经完成的通用能力准备；
6. 面经与 JD 资料分别关联到对应分支。

### 场景四：行动改变判断

1. 用户完成一次腾讯混元从业者访谈；
2. 航程记录完成事实与用户反思；
3. 事实自动进入腾讯混元分支的来源事件；
4. 泊泊提出“你可能喜欢平台型产品，但对跨团队协调有所顾虑”的证据建议；
5. 用户确认、纠正或拒绝该解释；
6. 罗盘更新分支证据、未知问题和最近变化，知识库保留访谈笔记引用。

## 20. 跨模块首版验收补充

- 对话可以从一句明确表达同时识别方向、公司、业务、岗位和约束；
- 本轮更新在右侧栏可见、可纠正、可撤销并有原话来源；
- 一个方向只创建一段方向航程，新增公司或业务时创建航程分支而不是重复航程；
- 航程始终包含一条通用主线，并能同时存在多个目标分支；
- 通用行动不会因增加分支而复制，分支只增加差异行动；
- 路径、日历和足迹都能按分支显示或筛选，首屏仍只突出一个行动；
- 航程结果按方向、分支或具体岗位准确回流罗盘；
- 知识库及时响应方向、分支、航程和岗位变化，在后台定向更新并建立关联；
- 知识库前端保留原有分类、搜索、资料卡和详情，不新增方向筛选条、分支标签或第二套导航；
- 同一知识对象可服务多个分支但只保存一份规范记录；
- 方向级与分支级收集任务分别去重，资料不会串入错误分支；
- 任何跨模块信息都只有一个权威来源，其他页面只引用，不产生可冲突副本。
