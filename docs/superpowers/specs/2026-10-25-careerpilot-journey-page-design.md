# CareerPilot 航程页设计

## 1. 设计意图

航程页把用户对职业的理解带进现实行动，再把真实经历带回罗盘。它不是通用待办软件，也不是只有截止日期的求职日历。

页面需要同时支持两类行动：

1. **职业探索行动**：职业访谈、体验任务、观察工作环境、验证一个职业问题；
2. **求职执行行动**：修改简历、准备笔试、参加面试、提交材料、跟进结果。

两类行动都必须能够回答“它属于哪段航程、为什么值得做”。用户可以同时进行多段航程，但首屏每次只聚焦其中一段，避免把并行探索变成任务堆积。

## 2. 关键产品决定

- `/journey` 固定默认打开“路径”视图；日历和足迹是同页可切换的次视图。
- 用户可以指定多段进行中的航程，例如“了解 AI 产品经理”和“准备阿里云产品岗面试”。
- 路径视图一次聚焦一段航程；日历聚合所有航程的时间事件；足迹默认聚合所有真实行动，也可按航程筛选。
- 首屏只强调一个“当前的一小步”，不展示完整任务清单。
- 日历只承载有明确时间意义的事件、截止日期和用户主动安排的行动；无日期探索行动留在路径中。
- 最小胜利和阻碍都可以进入足迹，但没有强制日记、连续打卡或“今天待填写”空卡。
- 心力重置是情境入口，不是第四个常驻模块。
- 所有外部 App 写操作继续遵守 `Preview → Confirm → Apply → Verify`，不能因用户曾经授权就跳过本次确认。

## 3. 方案选择

### 3.1 考虑过的方案

1. **路径为默认，多视图共享数据（已选）**
   - 路径保留产品的陪伴感与探索逻辑；日历负责时间安排；足迹负责真实回看。
   - 代价是需要统一的数据模型和跨视图状态同步。

2. **日历为默认**
   - 适合强截止期场景，但会让产品快速退化为日程工具，职业探索行动也会被迫绑定日期。

3. **按情境自动切换默认视图**
   - 看起来智能，但用户每次进入页面的空间位置不稳定，容易失去掌控感。因此不采用自动切换；只有明确的深链接可以直接打开某个次视图。

### 3.2 默认路由行为

- 直接进入 `/journey`：始终打开路径视图；
- 点击顶部“日历”或“足迹”：仅切换当前页面视图；
- 从某个日期、足迹或外部回执进入：允许通过稳定深链接打开目标，例如 `/journey?view=calendar&date=2026-10-28`；
- 普通刷新 `/journey` 不记忆上次视图，保持默认入口稳定；带有显式深链接参数时保留目标视图。

## 4. 页面框架

全站导航下方放置独立的局部视图切换器：

```text
[ 路径 Path ]   日历 Calendar   足迹 Footprints
```

- 切换器使用小型暖磨砂胶囊，不与全站导航合并；
- 三个视图共享动态山谷背景和当前用户状态，不进行整页跳转；
- 切换时保留当前航程选择，减少重复定位；
- 不使用一块覆盖整个页面的大玻璃，路径、时间锚点和行动卡均为独立材质面。

## 5. 默认视图：路径 Path

### 5.1 首屏目标

用户在五秒内应能看清：

- 当前聚焦的是哪段航程；
- 现在最值得做的一小步；
- 这一步在验证或推进什么；
- 最近是否存在不能错过的时间节点。

### 5.2 首屏构图

```text
┌────────────────────────────────────────────────────────────┐
│ CareerPilot       [首页 对话 罗盘 航程 知识库]        用户  │
│                                                            │
│                    [ 路径 ]  日历  足迹                     │
│                                                            │
│ JOURNEY 01                              NEXT MILESTONE      │
│ AI 产品经理                              OCT 28             │
│                                          从业者访谈          │
│ Clarity follows action.                  还有 3 天           │
│ 不是先想清楚，才出发。                                      │
│                                                            │
│                ○ 整理问题                                  │
│               ╱                                            │
│        泊泊  ●  联系一位从业者                              │
│             │  想验证：我是否喜欢处理模糊问题               │
│             │                                              │
│             │  [从这一步开始]  [和泊泊调整]                 │
│             ╲                                              │
│                ○ 完成交流 ───── ○ 写下真实感受              │
│                                                            │
│   已经走过 2 步                        向下查看完整航程 ↓     │
└────────────────────────────────────────────────────────────┘
```

背景延续暖色动态山谷，一条不规则小径从左下延伸到远景。当前节点附近略暖，未到达部分进入薄雾。路径是信息结构，不绘制成游戏关卡或完整地图。

### 5.3 航程身份与多航程切换

左上角显示当前聚焦航程：

```text
JOURNEY 01
AI 产品经理 ⌄
```

点击航程名称后，展开一组横向小卡：

```text
[AI 产品经理 · 当前]
[阿里云产品岗面试 · 2 天后]
[作品集完成 · 已停靠]
[＋ 新航程]
```

规则如下：

- 用户可以同时拥有多段 `active` 航程；
- `focused_journey_id` 只表示路径首屏当前聚焦项，不代表唯一活跃航程；
- 用户主动选择后更新当前聚焦，不由系统在进入页面时自动跳换；
- 其他航程出现新的临近节点时，只在切换卡上显示弱提醒，不强行抢走首屏；
- 新建航程优先来自罗盘或对话。`＋ 新航程` 会进入与泊泊的轻量创建对话，而不是打开项目管理表单。

### 5.4 品牌表达

首屏使用：

> Clarity follows action.<br>
> 不是先想清楚，才出发。

英文不承担功能说明，中文短句解释产品立场。功能性说明不超过一行，避免重复首页的大型品牌宣言。

### 5.5 行动路径

首屏展示当前航程最近的三至四个节点：

- 已经走过的节点：低亮光点；
- 当前节点：展开为主要行动卡；
- 下一节点：仅显示标题；
- 更远节点：进入薄雾，不提前暴露全部压力；
- 等待外部结果的节点：显示为空心环和 `等待回应`，不被视为逾期。

路径不显示完成百分比。`已经走过 2 步` 只是事实回顾，不构成进度承诺。

### 5.6 当前行动卡

当前节点展开为一张独立暖磨砂卡：

```text
联系一位 AI 产品从业者

想验证
我是否喜欢长期处理模糊问题？

做到这里就够了
发出一次真实邀请，不要求对方一定回复。

[从这一步开始]   [和泊泊调整]
```

卡片只包含：行动、原因或验证问题、可控的完成标准、两个主要动作。日期、附件、应用连接等信息放入展开详情，不堆叠在首屏。

完成标准必须描述用户可控制的行为。例如“发出一次邀请”而不是“成功约到从业者”。

### 5.7 首屏时间锚点

右上角放置独立的小型时间玻璃：

```text
NEXT MILESTONE
OCT 28
阿里云产品岗面试
还有 3 天
[查看日历 →]
```

- 这里显示所有活跃航程中最近的一个重要节点，并标注所属航程；
- 只有面试、笔试、访谈、明确截止日期或用户主动安排的行动才进入时间锚点；
- 没有近期节点时整块消失，不显示“暂无日程”；
- 点击后进入日历次视图并定位目标日期；
- 真正逾期才使用低饱和警示色，普通倒计时不使用红色。

### 5.8 泊泊在首屏中的角色

泊泊作为路径旁的小向导，不再占据首页级主视觉：

- 位于当前节点左下侧，保持轻微呼吸动画；
- 视线跟随当前节点而非持续追随鼠标；
- 行动开始后视线转向路径前方；
- 默认不弹气泡、不催促；
- 只有用户主动交互或系统检测到明确阻碍时，才出现轻量建议。

### 5.9 首屏动作

#### 从这一步开始

- 当前节点光晕轻微收束一次；
- 路径向前亮起一小段；
- 状态从 `ready` 变为 `in_progress`；
- 按钮变为 `记录一次推进`；
- 不启动倒计时，不产生持续计时监控。

#### 记录一次推进

原地展开：

```text
刚刚发生了什么？
[完成了一小步] [被什么挡住了] [这一步已经完成]
也可以写一句……
```

记录会进入足迹，并根据选择更新行动状态。普通“小胜利”不会自动把行动标为完成。

#### 和泊泊调整

进入对话页并携带当前行动、所属航程、验证问题和当前状态。输入框显示未发送的引导语：

> 这一步对我来说有点……

泊泊可以提出拆小、改期、暂停或替代行动；实际修改仍需要用户确认。

### 5.10 向下滚动

首屏之后依次呈现：

1. 当前航程的完整路径；
2. 正在等待回应的节点；
3. 其他进行中或暂时停靠的航程；
4. 最近几条行动足迹；
5. 进入完整足迹视图的入口。

首屏负责让用户愿意迈出一步，向下内容才负责完整管理。

## 6. 日历次视图 Calendar

### 6.1 视图定位

日历是航程数据的时间视图，不建立另一套任务。默认进入周视图，可切换月视图。

```text
十月 19 — 25                              [周 / 月]

一        二        三        四        五        六        日
                    22
                    ● 面试
          ○ 整理问题          ○ 记录感受

──────────────────────────────────────────────
临近节点
明天 14:00   阿里云产品岗面试       阿里云产品岗
还有 6 天    简历投递截止           国企求职
```

### 6.2 收录规则

日历只显示：

1. 有明确开始或结束时间的事件；
2. 有明确截止日期的事项；
3. 用户主动安排到某天的行动。

没有日期的探索行动不被自动塞入“今天”，也不出现持续打扰的空占位卡。

### 6.3 多航程呈现

- 日历默认聚合所有活跃航程；
- 每个事件显示所属航程短标签；
- 用户可以按航程筛选，但筛选状态不改变路径视图的聚焦航程；
- 不只依靠颜色区分航程，同时使用标签或形状；
- 同一天事件较多时先显示时间确定、临近截止和用户主动安排的内容，其余折叠为“还有 N 项”。

### 6.4 编辑和拖动

- 点击事件打开详情抽屉；
- 拖动可以调整站内计划时间，松开后显示原地保存确认；
- 已同步到外部 App 的事件调整时，必须明确选择“只改 CareerPilot”或“同时更新外部日历”；
- MVP 当前只具备外部日历创建能力，没有可靠更新能力时，不伪装为双向同步；改动后应提示外部事件仍保持原时间，并允许用户打开外部事件处理。

## 7. 足迹次视图 Footprints

### 7.1 视图定位

足迹不是“已完成任务”，而是用户真实发生过的行动、推进、阻碍和感受。

```text
10 月 25 日

● 和一位 AI 产品经理聊了 25 分钟
  “我喜欢讨论问题，但对频繁协调有些犹豫。”
  AI 产品经理 · 访谈行动

● 修完了作品集的项目背景
  一次小小推进

△ 被什么挡住了？
  “不知道应该联系谁。”
  泊泊建议：先从校友或朋友的朋友开始
```

### 7.2 最小胜利

用户可以记录修改一段简历、发出一次联系、写下三个问题、看完一份岗位描述等微小推进。记录只描述发生的事实，不自动派生新任务。

### 7.3 阻碍记录

用户可以记录：不知道下一步、害怕被拒绝、任务太大、精力不足、等待回应或环境不支持。泊泊可以帮助命名和拆解阻碍，但不会把每条阻碍自动转成行动。

### 7.4 无强制打卡

- 不显示连续记录天数；
- 不显示“今天还没记录”；
- 没有空白日记卡持续占据页面；
- 只有点击 `随手记一笔` 才展开输入；
- 没有记录的日期在时间线中自然略过。

### 7.5 复盘

行动完成后，泊泊先问一个低负担问题：

> 做完之后，你对这段航程的感觉更近了，还是更远了？

快速选择：

- 更想继续了解
- 有些地方和想象不同
- 暂时没有变化
- 不太适合我

用户可补充文字、语音或进入对话深聊。回答进入足迹，并形成罗盘更新建议；不会直接修改职业状态。

## 8. 心力重置

心力重置不是常驻视图，只在以下情况出现轻量入口：

- 用户连续推迟当前行动；
- 临近面试或重要截止日期；
- 用户主动记录焦虑、卡住或精力不足；
- 用户主动点击泊泊旁的心形入口。

展开内容：

```text
看起来这一步有点重。

[把它拆小一点]
[和泊泊说说]
[两分钟呼吸]
[今天先暂停]
```

`今天先暂停` 将行动设为 `paused` 并保留撤销，不显示失败，不扣除任何进度。两分钟呼吸是本地引导，不自动写入长期记忆；用户主动记录感受时才进入足迹。

## 9. 航程和行动状态

### 9.1 航程状态

```text
draft      尚未确认
active     正在进行
paused     暂时停靠
completed  已走完
archived   已归档
```

多段航程可以同时为 `active`。完成或归档航程不会删除其足迹、外部回执或罗盘证据。

### 9.2 行动状态

```text
ready       准备开始
in_progress 正在进行
waiting     等待回应
paused      暂时停靠
completed   已经走过
cancelled   不再需要
```

- `waiting` 不参与逾期提醒；
- `cancelled` 需要记录简短原因，但不要求长复盘；
- 外部 App 调用失败不会自动把行动标为失败或完成；
- 完成一次行动后可以产生后续建议，但不能自动创建下一行动。

### 9.3 焦点行动规则

一段航程可以同时存在多个 `in_progress` 或 `waiting` 行动，但路径首屏任何时候只突出一个 `focus_action_id`：

- 用户开始某个行动时，它自动成为该航程的焦点行动；
- 用户也可以从完整路径中主动选择 `设为当前一步`，这只改变首屏焦点，不改变行动状态；
- 焦点行动完成、取消、暂停或进入等待后，系统从已有行动中选出排序最靠前的 `ready` 行动作为“建议的下一步”并展示在首屏；
- 建议的下一步不会自动变成 `in_progress`，仍需用户点击 `从这一步开始`；
- 如果没有可继续的 `ready` 行动，首屏显示最近走过或等待中的节点，并提供 `和泊泊想一想`；
- 用户暂停一项行动时不会被系统立即催促开始另一项，新的建议只作为安静的可选入口；
- 不允许状态切换顺带创建新行动。任何新行动仍需单独确认。

## 10. 与其他页面的交互

### 10.1 首页

首页最多展示一条轻量入口：

> 下一小步 · 整理三个访谈问题

选择规则优先考虑用户当前聚焦航程，其次考虑最近的明确时间节点。点击进入对应行动。首页不显示任务列表、完成率或完整日历。

### 10.2 对话页

对话是航程的自然语言控制入口：

- 创建行动草案；
- 把行动拆小；
- 安排或调整时间；
- 记录完成、推进或阻碍；
- 进行完整复盘；
- 发起外部 App 操作预览。

泊泊先生成结构化建议卡，用户确认后才写入航程。普通聊天内容不会自动变成任务。

从航程进入对话时携带可见的上下文摘要，但不会自动发送用户消息；从对话返回后定位原航程和行动。

### 10.3 罗盘页

- 罗盘的具体职业和当前问题可以生成航程草案；
- 用户进入航程页编辑并确认后才创建正式航程或行动；
- 行动结果、最小胜利和复盘作为“你做过的”证据返回罗盘；
- 泊泊可以建议职业从“正在了解”变为“正在验证”或“暂时放下”，但排除、正式关联和关键状态变化仍由用户确认。

### 10.4 知识库

行动可以关联简历、岗位描述、面试资料、访谈提纲和作品集文件。关联仅建立引用，不复制文件。

行动产生的访谈笔记、复盘或文档可以预览后保存到知识库；临时附件不会因用于航程而自动永久保存。

### 10.5 Dreaming

Dreaming 可无确认地读取真实行动状态、阻碍和复盘线索，形成陪伴式观察，例如发现用户在哪类行动前经常停住、哪些微小行动能恢复动力。

Dreaming 不能自动修改日历、创建行动、调用外部 App、改变罗盘状态或将观察固化为高影响长期记忆。

## 11. 外部 App 调用设计

### 11.1 设计原则

外部 App 是行动的延伸，不成为新的一级导航。航程页只在任务情境中显示相关能力，例如有具体时间时显示“加入日历”，有访谈记录时显示“整理成文档”。

统一流程：

```text
提出调用 → 检查连接与授权 → 生成预览 → 用户确认
        → 执行 → 验证结果 → 返回可追溯回执
```

即使用户已授权某个 App，外部写入仍必须对本次具体内容确认。授权表示“可以提出并执行已确认的调用”，不表示允许自动写入。

### 11.2 当前 MVP 能力

#### 飞书日历

适用入口：日历事件详情、行动详情、对话建议卡。

- 创建面试、笔试、职业访谈或用户主动安排的事件；
- 预览必须显示标题、开始时间、结束时间、目标日历和所属航程；
- 用户确认后创建，验证成功才显示 `已加入飞书日历`；
- 保存外部事件引用与回执，不保存令牌；
- 当前只承诺创建，不声称双向同步或自动更新。

#### 飞书文档

适用入口：访谈提纲、行动复盘、航程总结。

- 先展示将创建的标题、内容摘要和目标位置；
- 用户确认后创建文档；
- 成功后可把文档链接关联回行动或足迹；
- 文档创建不等于自动加入 CareerPilot 知识库，永久索引仍需单独确认。

#### WPS 文档

适用入口与飞书文档一致。用户选择已连接的文档提供方后执行，不同时创建两份副本。MVP 只承诺创建 DOCX 文件，不承诺富文本持续同步。

#### 网易邮箱

当前只提供有界、只读的招聘邮件元数据搜索：发件人、主题、接收日期和不可逆消息标识摘要。

- 用户可以在某段求职航程中点击 `查找相关招聘邮件`；
- 结果可以建议关联到面试或等待回应节点；
- 不读取或展示邮件正文与附件；
- 不发送、回复、转发邮件；
- 邮件结果不会自动写入长期记忆，也不会未经确认创建日历事件。

### 11.3 外部调用预览

外部写入统一使用右侧或底部预览抽屉：

```text
将创建一个飞书日历事件

账号       已连接的飞书账号
标题       阿里云产品岗面试
时间       10 月 28 日 14:00–15:00
目标日历   主日历
关联航程   阿里云产品岗面试

[取消]                       [确认创建]
```

用户确认后按钮进入执行状态。结果分为：

- `completed`：显示外部链接与已验证回执；
- `failed`：显示可读错误并允许安全重试；
- `unknown`：明确说明无法确认是否创建成功，不自动重试，以免产生重复事件或文档。

### 11.4 未连接状态

如果能力未连接或未授权：

- 动作仍可作为建议存在；
- 点击后解释本次需要的具体权限和用途；
- 用户连接完成后返回原行动与原预览；
- 不把“连接所有 App”作为使用航程页的前置条件；
- 用户可以始终选择只保存在 CareerPilot 内。

### 11.5 未来扩展

未来可通过同一能力层接入 Outlook Calendar、Google Calendar、飞书任务或其他邮件提供方，但 UI 只根据后端实际返回的已配置能力展示，不提前显示不可用入口。

消息发送、邮件发送、替用户联系陌生人属于更高风险能力，不在本轮范围内；未来即使增加，也必须逐次预览收件人和正文并确认。

## 12. 建议的数据模型

### 12.1 Journey

```text
Journey

- title

- status
- related_career_id?
- related_job_id?
- focus_action_id?
- created_at
- updated_at
```

`focused_journey_id` 属于用户界面偏好，可单独存储；多段航程可以同时活跃。

### 12.2 JourneyAction

```text
JourneyAction
- id
- journey_id
- title
- purpose
- verification_question?
- done_definition
- state
- scheduled_start?
- scheduled_end?
- due_at?
- sort_order
- created_at
- updated_at
```

### 12.3 JourneyEvent

```text
JourneyEvent
- id
- journey_id
- action_id?
- type: progress | blocker | completion | reflection | external_receipt
- summary
- detail?
- occurred_at
- source_type
- source_id?
```

### 12.4 ExternalLink

```text
ExternalLink
- id
- journey_id
- action_id?
- provider_id
- capability
- external_reference
- receipt_status
- external_url?
- created_at
```

外部引用只保存完成产品体验所需的最小元数据，不保存凭据、邮件正文或完整外部文档内容。

## 13. 建议的接口边界

- `GET /v1/me/journeys`：返回多航程摘要与用户当前聚焦项；
- `POST /v1/me/journeys`：确认创建航程；
- `PATCH /v1/me/journeys/{id}`：状态与基础信息；
- `POST /v1/me/journeys/{id}/actions`：确认创建行动；
- `PATCH /v1/me/journey-actions/{id}`：状态、时间与完成标准；
- `POST /v1/me/journey-actions/{id}/events`：记录推进、阻碍、完成或复盘；
- `GET /v1/me/journey-calendar?from=&to=&journey_id=`：聚合日历数据；
- `GET /v1/me/journey-events?journey_id=&cursor=`：足迹时间线；
- 外部调用复用现有 `/v1/me/actions/preview`、确认与执行接口，不从 Journey API 绕过治理边界。

所有写请求支持幂等键。列表采用稳定排序与游标，避免路径、日历和足迹在后台刷新时乱跳。

## 14. 数据一致性与冲突

- 路径、日历、足迹读取相同 Journey/Action/Event 数据，不在前端维护三份副本；
- 用户在日历中调整站内时间后，路径卡的时间同步更新；
- 外部日历创建成功后保存不可变回执，后续站内修改不假装已同步；
- 两个页面同时编辑同一行动时使用版本号或更新时间检测冲突；
- 发生冲突时保留用户输入，展示“此行动刚在另一处更新”，允许重新应用；
- 删除航程采用归档优先。真正删除前说明将影响足迹、外部引用和罗盘证据；外部事件不会因为站内删除而自动删除。

## 15. 空状态、加载与失败

### 15.1 无航程

```text
还没有需要赶路的地方。

当某个职业问题值得用真实行动确认时，
泊泊会和你一起设计第一小步。

[和泊泊聊聊]   [回到罗盘]
```

背景只保留一个未点亮起点，不要求用户填写项目表单。

### 15.2 有航程但无当前行动

显示最近走过的节点和一句：`这段航程暂时没有下一步。` 提供 `和泊泊想一想`，不自动创建行动。

### 15.3 加载

使用与最终路径、时间锚点相同位置的低对比轮廓，避免数据到达后大幅位移。背景动态可以先加载，交互区域在数据就绪前不可点击。

### 15.4 失败

- 单个行动更新失败时在原卡片重试，不刷新整页；
- 足迹保存失败时保留原文；
- 外部调用失败与站内行动状态分离；
- 不用全局 toast 作为唯一反馈。

## 16. 响应式设计

### 16.1 桌面端（≥ 1100px）

- 保留山谷路径、多航程横向切换、右上时间锚点和低幅视差；
- 当前行动卡沿路径展开；
- 外部调用使用右侧抽屉。

### 16.2 平板端（720–1099px）

- 航程切换改为顶部横滑卡；
- 时间锚点移动到当前行动下方；
- 路径减少弯折，保持清晰；
- 外部调用使用底部抽屉。

### 16.3 移动端（< 720px）

- 背景保留静态或低频雾层，取消复杂鼠标视差；
- 路径改为纵向节点；
- 局部视图切换固定在导航下方；
- 周历使用横向日期带，月历按需展开；
- 足迹为单列时间线；
- 多航程切换使用全宽底部面板。

## 17. 可访问性与减少动态

- 路径节点同时提供线性 DOM 顺序，屏幕阅读器不按视觉坐标朗读；
- 所有拖动操作都有按钮或键盘替代；
- 不只依靠颜色表达航程、状态或逾期；
- 毛玻璃上的文字保持足够对比度，背景在文字区域自动压暗；
- 尊重 `prefers-reduced-motion`，关闭视差、路径光线移动和节点飞行动画；
- 视图切换、行动状态变化和外部调用结果提供可读状态通知；
- 抽屉正确管理焦点并支持 `Esc` 关闭。

## 18. 非目标与反目标

本轮不做：

- 通用团队项目管理；
- 完成百分比、燃尽图或绩效评分；
- 连续打卡与每日强制复盘；
- 自动把每条聊天、想法或阻碍转成任务；
- 自动替用户发送消息、邮件或联系陌生人；
- 未经确认写入或修改外部 App；
- 声称不存在的双向日历同步；
- 在航程页内复制完整聊天、罗盘或知识库界面。

即使功能齐全，如果首屏让用户感到“又多了一个要维护的任务系统”，或者泊泊不断提醒造成压力，都视为设计失败。

## 19. 验收标准

- `/journey` 默认固定打开路径视图；日历和足迹可在同页切换；
- 用户可以同时指定多段活跃航程，并主动切换路径首屏的聚焦航程；
- 首屏只突出一个可控的当前行动，同时保留一个全局最近时间锚点；
- 日历聚合多航程，但只收录有明确时间意义的内容；
- 足迹可以记录最小胜利和阻碍，没有强制打卡；
- 心力重置只在情境中出现；
- 罗盘、对话、首页、知识库和 Dreaming 的数据与确认边界明确；
- 飞书、WPS、网易邮箱能力按后端真实可用状态展示；
- 所有外部写入逐次预览、确认、执行并验证；
- 外部失败或不确定结果不会污染站内行动状态；
- 桌面端具有动态路径感，移动端与减少动态模式仍可完整操作。
