# 情绪识别与回应控制

CareerPilot 当前没有使用独立的情绪分类模型，也不尝试推断用户的心理状态。系统采用一套可审查的规则基线，从当前消息中识别与支持方式有关的显式信号，再把结果转换成检索、工具和回答约束。

这套机制的目标不是给用户贴情绪标签，而是回答两个运行时问题：这一轮应该倾听、梳理、探索还是行动？是否出现了必须优先处理的安全风险？

## 1. 系统边界

当前实现只处理与本轮回应有关的有限信号：

- 困扰信号，例如“焦虑”“难受”“害怕”“自责”；
- 明确的支持偏好，例如“只想说说”“不要建议”“帮我梳理”；
- 明确的行动请求，例如创建提醒或加入日历；
- 试探性兴趣，例如“有点想做”“想试试”；
- 绝对化负面自我判断，例如“肯定做不了”“完全没能力”；
- 自伤或自杀相关的安全风险表达。

它不进行心理疾病诊断，不计算长期“情绪画像”，也不把一次负面表达当作稳定人格、能力或职业倾向。规则命中代表“需要采用更保守的回应策略”，不代表系统已经准确知道用户的真实感受。

## 2. 处理链路

```text
当前用户消息 + 可选的用户指定模式
        │
        ▼
SupportPolicy
  ├─ 识别安全风险与困扰信号
  ├─ 决定 listen / organize / explore / act
  └─ 决定是否允许行动工具
        │
        ▼
RuleBasedIntentInterpreter
  ├─ 识别当前任务意图
  └─ 将困扰作为必要的次级意图保留
        │
        ▼
ResponseStrategyEngine
  ├─ 生成有限的 AffectAppraisal
  ├─ 选择本轮回答动作
  └─ 约束温度、主动性、篇幅、追问和排版
        │
        ├────────► IntentAwareRetrievalRouter
        │            限制记忆、知识和工具使用
        ▼
PromptComposer
  将安全、支持模式和回答契约编译进模型上下文
```

主入口位于：

- `src/careerpilot/support/policy.py`
- `src/careerpilot/support/response_strategy.py`
- `src/careerpilot/context/intent.py`
- `src/careerpilot/context/router.py`
- `src/careerpilot/agent/prompt.py`

## 3. 支持模式决策

`SupportPolicy` 先检查安全风险，再处理用户明确指定的模式，最后才根据消息中的显式标记推断模式。

优先级如下：

```text
安全风险
→ 用户明确指定的支持模式
→ 明确倾听请求
→ 明确行动请求
→ 梳理请求
→ 探索请求
→ 一般困扰信号
→ 默认 organize
```

最终产生 `SupportDecision`：

| 字段 | 含义 |
|---|---|
| `mode` | 本轮支持模式：`listen`、`organize`、`explore` 或 `act` |
| `distress_detected` | 是否命中困扰或安全风险信号 |
| `safety_risk_detected` | 是否命中自伤、自杀等安全风险信号 |
| `action_tools_allowed` | 本轮是否允许暴露行动工具；只有非安全风险的 `act` 模式为真 |

安全风险是硬覆盖项。即使调用方明确请求 `act`，系统也会切换到 `listen` 并关闭行动工具。普通困扰信号不会覆盖用户明确提出的梳理或行动目标；例如“我很焦虑，但请帮我梳理”仍可进入 `organize`。

## 4. 回应策略

`ResponseStrategyEngine` 不直接生成回复，而是生成可检查的 `ResponseContract`。其中的 `AffectAppraisal` 只是一组回答控制变量，包括情绪效价、强度、可控性和主要事件类型，不是用户档案，也不会单独持久化。

当前主要策略如下：

| 当前信号 | 回答动作 | 关键限制 |
|---|---|---|
| 安全风险 | 优先确认即时安全 | 禁止职业分析、职业规划和工具调用 |
| `listen` | 倾听并具体映照 | 不给建议、不做行动计划、不连续追问 |
| 绝对化负面自我判断 | 接住担忧，再区分情境、感受、判断和证据 | 不反驳、不强行积极改写、不做诊断 |
| 试探性兴趣 | 先映照兴趣，再探索来源 | 不做长篇职业科普，不提前制定计划 |
| `explore` | 探索可能性和证据 | 不抢先给出适配结论 |
| `organize` | 帮助梳理 | 不替用户下结论 |
| `act` | 推进一个可确认的小行动 | 需要时只询问确认信息 |

回答契约还控制默认篇幅、最多追问数量、是否使用标题和项目符号。倾听和安全场景默认不用小标题或列表，避免把支持性回应写成报告。

CBT-informed 策略只在同时命中绝对化表达和负面自我判断时启用。它要求区分“发生了什么、有什么感受、做了什么判断、现有证据是什么”，但不得把 CareerPilot 描述成心理治疗，也不得把用户的判断直接复述成事实。

## 5. 对检索与工具的影响

支持模式不仅改变措辞，也改变系统可使用的上下文和工具。

- `listen` 默认不检索长期记忆、职业知识或网页；只有用户明确引用历史时，才允许读取相关个人记忆。
- `listen` 不暴露职业知识搜索工具，也不允许行动工具。
- `organize`、`explore` 和 `act` 仍由任务意图决定是否读取 Memory、认知状态、私有文档或职业知识。
- 任何安全风险都会关闭外部行动，并要求回答优先确认即时危险。

因此，“识别到困扰”不会自动加载更多隐私数据。相反，倾听模式会主动缩小上下文范围。

## 6. 与长期记忆的边界

情绪识别结果不等于长期记忆。`MemoryWritePolicy` 只接受用户明确表达的、具有持续性的目标、偏好、约束、经历、决定或想法。一次“我很焦虑”“我太差了”不会因为命中情绪规则而被保存成稳定事实。

如需保存支持偏好，用户需要表达具有持续性的要求，例如“以后我焦虑时请先听我说”。即使如此，保存的也是用户明确提出的支持偏好，而不是系统推断出的心理特征。

## 7. 安全处理

安全风险词命中后，当前实现执行以下硬约束：

1. 强制切换为 `listen`；
2. 设置 `safety_risk_detected=true`；
3. 设置 `action_tools_allowed=false`；
4. 禁止职业分析、检索和外部行动；
5. 先表达关切，并用一个简短问题确认用户是否处于立即危险中；
6. 如有即时危险，建议联系当地紧急服务和一位能够到场的可信任人士，不假定国家，也不编造热线号码。

这是一条保守的文本安全路由，不是临床风险评估。规则未命中不代表不存在风险；任何依赖该能力的上线场景都应继续采用人工升级、地区化资源和安全评测。

## 8. 已知限制

当前规则基线具有清晰、确定、易测试的优点，也有明确局限：

- 依赖有限的中文关键词，不能可靠处理隐喻、反讽、错别字、方言或跨语言表达；
- 不能稳定区分词语是在描述自己、转述他人还是讨论假设场景；
- `AffectAppraisal` 目前是由离散策略分支赋值，不是连续、经过校准的情绪估计；
- 不输出情绪概率，也没有基于真实用户分布验证的召回率或误报率；
- 单轮规则对上下文变化的理解有限，主要依赖当前消息和用户明确指定的模式；
- 安全词表只能作为最低保护层，不能替代更完整的危机识别和人工处置流程。

因此，产品和文档中应称其为“情绪信号识别与回应控制”或“规则式情绪感知”，不应宣称为高准确率情绪识别模型。

## 9. 测试与变更要求

当前测试入口：

- `tests/support/test_policy.py`：支持模式、困扰信号和安全覆盖；
- `tests/support/test_response_strategy.py`：回应动作、CBT 触发、排版与禁止项；
- `tests/context/test_intent.py`：情绪支持与任务意图的组合；
- `tests/memory/test_write_policy.py`：短暂困扰不得进入长期记忆；
- `tests/evaluation/`：端到端支持模式和安全检查。

新增或修改规则时，至少应覆盖：命中样例、相近但不应命中的反例、用户明确模式的优先级、安全风险覆盖、检索与工具权限，以及临时情绪不进入长期记忆。规则词表变化会直接改变产品行为，必须通过测试提交，不能只修改 Prompt。

## 10. 来源与许可

`response_strategy.py` 中“有限评估结果与回答控制分离”的边界参考了 `Elaine-wy/emoai-affect-engine` 所记录的概念，CareerPilot 使用独立 Python 实现，并将安全、记忆、任务权限和人格边界保留在自身架构中。许可说明见仓库根目录的 [THIRD_PARTY_NOTICES.md](../../THIRD_PARTY_NOTICES.md)。
